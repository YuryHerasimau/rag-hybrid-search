# Методология оценки (Evaluation)

Оценка — сердце проекта, а не приложение к нему. Цель: (1) численно доказать
вклад каждого приёма (ablation) и (2) не допустить деградации при изменении
промптов/чанкинга через CI-гейт.

## Метрики (Ragas)

- **faithfulness** — насколько ответ опирается на предоставленный контекст
  (прямой прокси галлюцинаций).
- **answer_relevancy** — релевантность ответа вопросу.
- **context_precision** — доля релевантного в retrieved-контексте.
- **context_recall** — насколько retrieved покрывает нужную информацию.

Первые две оценивают генерацию, вторые две — retrieval. Это позволяет понимать,
*где* именно теряется качество.

## Golden-набор

1. Сгенерировать synthetic Q&A из корпуса через **Ragas testset generation**.
2. Вручную почистить до ~50–100 качественных пар.
3. Заверсионировать в JSON (`eval/golden/`), коммитить в репозиторий — это
   фиксированный контракт для регрессий.

## Ablation

После каждой фазы прогоняем полный golden-набор и добавляем строку в таблицу в
[README](../README.md#ablation-study). Так виден изолированный вклад hybrid,
reranker и семантического чанкинга.

## CI-гейт (Фаза 6)

GitHub Actions на PR:

1. Прогон eval на **подмножестве** golden-set (~20 вопросов) — экономия времени
   и денег.
2. **LLM-judge на Claude Haiku** — дёшево.
3. Сравнение метрик с зафиксированным baseline; **PR красный**, если метрика
   упала ниже порога.

Практика для дешёвого и быстрого CI:
- API-ключ в секретах репозитория;
- кэшировать эмбеддинги как артефакт;
- гонять подмножество, а не весь набор;
- judge — на Haiku, не на Sonnet.
