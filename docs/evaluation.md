# Методология оценки (Evaluation)

Оценка — сердце проекта, а не приложение к нему. Цель: (1) численно доказать
вклад каждого приёма (ablation) и (2) не допустить деградации при изменении
промптов/чанкинга через CI-гейт.

## Метрики

Используем стандартные RAG-метрики (считаем их сами, без ragas — см. ниже):

- **faithfulness** — насколько ответ опирается на предоставленный контекст
  (прямой прокси галлюцинаций).
- **answer_relevancy** — релевантность ответа вопросу.
- **context_precision** — доля релевантного в retrieved-контексте.
- **context_recall** — насколько retrieved покрывает нужную информацию.

Первые две оценивают генерацию, вторые две — retrieval. Это позволяет понимать,
*где* именно теряется качество.

## Golden-набор

Q&A размечаются вручную и версионируются в JSON (`eval/golden/`) — фиксированный
контракт для регрессий. Два набора:

- `deliveryservice.json` — по срезу реальной вики (локально, корпус не в репо);
- `synthetic.json` — по синтетическому корпусу `eval/corpus/` (вымышленный
  продукт «Орбита»), который **коммитится** — на нём работает CI.

Поля элемента: `question`, `relevant_sources` (метки для retrieval-метрик),
`answerable` (false — проверка abstention), опц. `ground_truth`.

## Ablation

После каждой фазы прогоняем полный golden-набор и добавляем строку в таблицу в

## Метрики — как считаются (без ragas)

Ragas не используем — считаем сами, прозрачно:

- **Retrieval** (`rag.eval.metrics`) — детерминированно, без API: по
  `relevant_sources` считаем hit@k, MRR, recall@k, precision@k (source-level,
  чанки одного файла схлопываются). `precision@k` при ~1 релевантном источнике
  на вопрос — вспомогательный сигнал; основные — hit@k, MRR, recall@k.
- **Generation** (`rag.eval.judge`) — свой лёгкий LLM-судья на Haiku:
  faithfulness (опора на контекст) и answer_relevancy через `structured_predict`
  (видимый промпт). Плюс `abstention_accuracy` — детерминированно (решение
  отвечать/воздержаться против `answerable`).

## Human-in-the-loop (ручная сверка + валидация судьи)

Авто-судья дёшев, но сам по себе — ещё одна LLM. Чтобы доверять ему в гейте, его
вердикты периодически сверяются с человеком на реальном корпусе (`rag.eval.human`,
вне CI). Поток из трёх шагов:

1. `uv run python -m rag.eval.human run --judge` — прогоняет вопросы
   (`eval/human/questions.json`) через `hybrid + rerank` и grounded-ответ
   (по умолчанию Sonnet, как в проде); печатает по каждому ответ / цитаты /
   висячие источники / top-источники и пишет `eval/human/results.json` с пустыми
   полями под ручной вердикт. `--judge` добавляет оценку Haiku-судьи для сверки.
2. Человек проставляет в `results.json` (`1` — да, `0` — нет, `null` — не оценивать):
   - `human_correct` — ответ фактически верен;
   - `human_grounded` — опирается на источники без выдумок (для воздержаний `null` —
     оценивать нечего);
   - `human_abstention_ok` — решение отвечать / воздержаться уместно.
3. `uv run python -m rag.eval.human score` — человеческие метрики и, главное,
   **согласие человек↔судья** по groundedness.

Зачем: расхождение авто-судьи с человеком означает, что метрике `faithfulness` в
CI доверять нельзя; высокое согласие валидирует дешёвый гейт. Диагностика разводит
три типа провала: промах retrieval (нужного файла нет в top-источниках),
перестраховка генерации (контекст релевантен, но модель воздержалась) и
галлюцинация (`human_grounded=0` и/или непустой `unsupported_citations`).

> `eval/human/results.json` — в `.gitignore`: содержит ответы по реальной
> (приватной) вике. Коммитится только `questions.json` (формулировки вопросов).

## CI-гейт (Фаза 6, Шаг 3)

`.github/workflows/eval.yml` на push в main и на PR:

1. Линт (ruff) + юнит-тесты.
2. Сборка индекса на **синтетическом** корпусе `eval/corpus/` (реальная вики в
   репозиторий не попадает).
3. `rag.eval --golden synthetic.json --gate` — сверка метрик с порогами
   `eval/baseline.json`; метрика ниже порога → **exit 1 → PR красный**.
4. Generation-гейт — доп. шаг, включается только при наличии секрета
   `ANTHROPIC_API_KEY` (судья на Haiku — дёшево).

Практика для дешёвого и быстрого CI:
- веса моделей (e5 + reranker) кэшируются между прогонами;
- retrieval-гейт не требует API (всегда зелёный путь);
- generation-гейт — на подмножестве (`--limit`), judge на Haiku.
